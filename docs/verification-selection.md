# Выбрать проверки по изменениям

`task:verify plan` сравнивает изменения с базовым коммитом и печатает план проверок.
Выполни выбранные команды отдельно: планировщик их не запускает.

Репозиторий описывает свои проверки в `task-verification.json`. Общий реестр
[workspace-verification.json](../config/workspace-verification.json) хранит
репозитории и связи между ними. В шаблоне tooling подключён, releases ожидает
подключения. Для планирования нужны коммиты и локальная ветка `master`.

## Получить план

Из `w-tooling` после появления первого коммита с manifest:

```sh
npm run task:verify -- plan \
  --repository w-tooling --repository-root "$PWD" \
  --profile affected --base "$(git merge-base HEAD refs/heads/master)"
```

Для другого репозитория передай его имя, точный Git-корень и базовый SHA.
Дополнительно нужен `--registry-base` с базовым SHA tooling. База вычисляется
как `git merge-base HEAD refs/heads/master` в соответствующем репозитории.
Для подключённого сервиса она также должна совпадать с `revision` в реестре.

| Профиль | Когда использовать |
| --- | --- |
| `affected` | После локального исправления |
| `testing` | После серии исправлений |
| `pr` | Перед передачей на проверку или слиянием |
| `release` | Перед выпуском |

Каждый следующий профиль включает предыдущий. Во всех профилях учитываются
зависимые области и связанные репозитории. Обязательный сквозной сценарий задачи
добавляется к этому плану.

`--boundary ID` добавляет полный набор указанной границы. `--registry PATH`
выбирает другой реестр. `--json` выводит подробности. По умолчанию видны причины
выбора, блокеры и следующий шаг; команды показаны как `cwd` и массив `argv`.

## Описать проверки репозитория

Пример `task-verification.json` для репозитория с одной общей проверкой:

```json
{
  "$schema": "../w-tooling/config/task-verification.schema.json",
  "schemaVersion": 1,
  "kind": "repository",
  "repository": "search-worker",
  "status": "active",
  "policy": {"fallbackBoundary": "repository-full"},
  "actions": {"repository-full": {"kind": "automatic", "argv": ["npm", "test"], "cwd": "."}},
  "areas": {"source": {
    "paths": ["**"], "dependsOn": [],
    "coverage": {
      "affected": ["repository-full"], "testing": ["repository-full"],
      "pr": ["repository-full"], "release": ["repository-full"]
    }
  }},
  "boundaries": {"repository-full": {"actions": ["repository-full"]}},
  "metaGate": {"actions": ["repository-full"], "profiles": ["affected", "testing", "pr", "release"]},
  "inputs": {},
  "exports": {}
}
```

Замени `argv` своей командой. `automatic` описывает команду; ручные, внешние
и меняющие состояние проверки объявляй как `obligation` с `obligationType`
(`manual`, `external`, `stateful`) и причиной в `reason`.

`areas` связывает пути с проверками и зависимостями. Каждый изменённый путь
должен принадлежать одной области. Допустимые glob: `*`, `**`, `?`.
Неизвестный или неоднозначный путь потребует явной полной границы.
`metaGate` проверяет сам выбор тестов; `inputs` и `exports` описывают связи.
Имена используют kebab-case. Точный формат хранится в
[JSON Schema](../config/task-verification.schema.json).

## Подключить репозиторий и связи

1. Опиши фактические проверки и области в manifest, проверь полный набор
   прежним способом и включи manifest в `master`.
2. Добавь репозиторий в общий реестр с `status: active`, `enrollment: pending`.
   `root` считается от каталога реестра, `manifest` от корня репозитория.
3. Проверь план на удалении и переименовании файлов, неизвестном пути, циклах
   зависимостей и недоступном связанном репозитории.
4. В задаче владельца реестра укажи полный SHA в `revision` и поставь `enrollment: enrolled`.
   Нужен чистый checkout на этом SHA; manifest уже должен находиться в `HEAD`.

Сам владелец реестра обходится без `revision` в собственной записи. Его версию
задаёт `--registry-base`. `reserved` резервирует имя; `historical` и `unmanaged`
исключают репозиторий из действующего процесса.

Связь соединяет export или путь производителя с input потребителя.
`exact-copy` сравнивает обычные файлы по байтам и исполняемости. Для `generated`,
`compatibility` и `artifact` укажи действие проверки либо явную обязанность.
Удаление связи в рабочей версии сохраняет проверку её базового варианта.
Пересечение областей можно временно разрешить исключением с владельцем,
причиной и датой окончания; межрепозиторные связи исключений не поддерживают.

Обновляй закреплённый SHA отдельной задачей владельца реестра. При этом меняется
только `revision`; новый SHA должен совпадать с чистым HEAD и доверенной базой
связанного checkout. Допускаются переход к потомку и откат к предку.
Планировщик включит полные проверки обеих версий.

## Разобрать результат

| Результат | Следующий шаг |
| --- | --- |
| `planned` | Выполнить выбранные проверки |
| `no_changes` | Изменений относительно базы нет |
| `requires_boundary` | Добавить предложенный `--boundary ID` и повторить команду |
| `action_required` | Выполнить ручную, внешнюю или меняющую состояние проверку |
| `blocked` | Устранить причину из отчёта, затем повторить план |
| `unverified` | Завершить подключение или восстановить отсутствующий checkout |
| `not_applicable` | Выбрано зарезервированное имя |

При `BOOTSTRAP_REQUIRED` сначала включи manifest в основную ветку, проверив его
прежним полным набором. При `CANDIDATE_DRIFT` останови параллельную запись и повтори
команду. `BASE_REVISION_UNTRUSTED` и `REGISTRY_BASE_UNTRUSTED` требуют заново вычислить
базовый SHA. `REGISTRY_CONFOUNDER` означает, что изменения tooling нужно проверять
отдельно от задачи сервиса.

## Что требуется от checkout

План учитывает коммиты после базы, индекс, рабочие и новые файлы. Обе стороны
переименования и прежние определения проверок сохраняются в плане.
Связанные checkout должны быть чистыми и совпадать с закреплёнными SHA.
Ошибки схемы, ссылок или циклы зависимостей останавливают построение целиком.

Символические ссылки, активные submodules, скрытые пути индекса и преобразующие
Git-фильтры или attributes мешают доказать состав файлов; планировщик их отклоняет
с кодом причины. Используй checkout с обычными файлами и прозрачными настройками Git.
Локальные ignore-правила вне `.gitignore` не скрывают изменения; служебное исключение
составляет `.project/task-runs/**`.

Пределы чтения: 1 МиБ для конфига, 32 МиБ для файла, 256 МиБ суммарно и 120 секунд
на построение. Превышение возвращает код `*_TOO_LARGE`,
`CANDIDATE_READ_BUDGET_EXCEEDED` или `CANDIDATE_READ_TIMEOUT`.
